## Что и зачем

На защите спросят «почему не Telegram», «почему не GigaChat», «зачем своя GPU», «что если модель упадёт». Каждый ответ ниже опирается на запись в журнале или в коде. Главный принцип, из которого вытекает почти всё: **правила держит код, а не промпт**. Модель только формулирует текст, а куда отправить, что скрыть и что считать ответом, решает код.

## Решения

### 1. Мессенджер MAX и long polling

| | |
|---|---|
| **Решение** | бот в MAX; сообщения получаем long polling (бот сам спрашивает MAX «есть новое?») |
| **Почему** | MAX — условие кейса. По Mediascope за июнь 2026 месячный охват MAX 86,3 млн против 75,7 млн у Telegram (`qa.md` №12). Long polling работает без своего домена с сертификатом |
| **Отвергли** | webhook: нужен домен с TLS на 443, а одновременно с polling его использовать нельзя |
| **Цена** | MAX называет long polling «не для production»; для пилота нужен webhook и домен. Ещё грабли: без корневого сертификата Минцифры API MAX не пускает — первый запрос упал именно на этом |

### 2. Вход только по персональной ссылке

| | |
|---|---|
| **Решение** | сотрудник подключается по ссылке или QR из оффера; «Начать» без ссылки бот игнорирует |
| **Почему** | в API MAX не описано, что бот может написать первым. QR в оффер требует само ТЗ (r8). Бот пишет только тем, кто подтвердил себя |
| **Отвергли** | «бот пишет первым по номеру» |
| **Цена** | рекрутер должен передать ссылку; если сотрудник её не открыл, бот молчит (в обзоре это «не подключился») |

### 3. Go для бота и правил, Python только для ML

| | |
|---|---|
| **Решение** | бот, планировщик, правила и эскалации — на Go (Fiber, GORM, Postgres); поиск, OCR, реранкер, разметка и голос — Python-сервис; кабинет — Vue 3 |
| **Почему** | решение человека 23.10: стек и конвенции взяты из прошлого проекта команды (`hack-ru-clinik`). Официальный Go-клиент MAX живой, лицензия Apache-2.0 |
| **Отвергли** | Python-бэкенд из ресерча (`maxapi` + FastAPI + APScheduler) |
| **Цена** | две кодовые базы. Риск по п. 4.1.2 Положения («нет заранее заготовленного кода»): конвенции и шаблоны взяты из прошлого проекта, ответ на «кто писал» нужно держать готовым (`gaps.md` S4) |

### 4. Своя открытая модель T-lite на RunPod вместо публичных ИИ

| | |
|---|---|
| **Решение** | открытая модель T-lite-it-2.1 (Т-Банк, Apache-2.0, 8B, FP8) на vLLM, развёрнутая нами на арендованной GPU RunPod |
| **Почему** | материалы заказчика конфиденциальны, сторонние ИИ-сервисы не используем (п. 4.3.2 Положения). Модель влезает в одну карту на 24 ГБ, значит в пилоте её можно поставить в контур заказчика. T-lite — сильная открытая модель для русского |
| **Отвергли** | GigaChat, YandexGPT и другие внешние API для закрытой базы. При этом клиент стандартный: адрес модели меняется одной переменной |
| **Цена** | под стоит $1,09/ч (~2,5 тыс. ₽ в сутки, `qa.md` №26) и физически в США — «on-prem» говорить нельзя. Облачные API в 5–50 раз дешевле своей GPU; довод за свою — риск штрафа за утечку ПДн (от 3 млн ₽), выбор за ИБ заказчика. Под общий с соседним хакатоном, решение человека — держать включённым |

### 5. Бот работает и без модели

| | |
|---|---|
| **Решение** | модель — необязательная часть. Без неё бот отвечает дословной цитатой пункта, а сценарии, опросы и обращения не зависят от неё |
| **Почему** | падение пода на сцене не должно ломать продукт; правило «код решает, модель формулирует» |
| **Отвергли** | ответы «только моделью» |
| **Цена** | без модели хуже понимаются разговорные вопросы |

### 6. Ответ только с пунктом и проверкой кодом

| | |
|---|---|
| **Решение** | порог реранкера 0,2; код проверяет цитату и каждое число в ответе; переформулировка вопроса с двумя защитами |
| **Почему** | выдуманный срок или сумма хуже передачи человеку. Порог 0,1 пропускал ловушку «компенсируют ли проезд» |
| **Отвергли** | более низкий порог ради охвата; переформулировку без защит (она пропускала 20 % ловушек) |
| **Цена** | на новых разговорных вопросах бот находит пункт в 59–68 % случаев, остальное уходит человеку |

### 7. «Дальше →» по умолчанию

| | |
|---|---|
| **Решение** | каждое сообщение блока без вопроса, за которым есть ещё сообщения, получает «Дальше →»; сотрудник листает блок как карточки |
| **Почему** | решение человека 24.10 «против спама». В ТЗ блоки по 10+ реплик; подряд они превратились бы в стену текста, а MAX режет скорость до 2 сообщений в секунду. Нажатие показывает, что человек читает |
| **Отвергли** | деление по длине текста; отправку подряд с «печатает…» (осталась ручной настройкой HR, и даже там не больше двух подряд) |
| **Цена** | сотруднику больше нажатий; если он не жмёт, блок стоит до следующего блока |

### 8. Вопрос держит поток, ветка живёт в кнопке

| | |
|---|---|
| **Решение** | блок идёт как диалог: вопрос ждёт ответа → правка в «✅ …» → ветка до двух реплик → следующая реплика. Ветка — часть кнопки, глубина не больше двух, ветки всегда сходятся |
| **Почему** | внешний ресерчер разобрал ТЗ построчно: 68 строк, глубина веток ≤ 2, «иначе» не встречается, «Следующая реплика» — порядок, а не ветка (`2026-10-24-branching-verdict.md`) |
| **Отвергли** | модель «дочерний шаг» из первого разбора ТЗ (`05-excel-tz-mapping.md` §3.2) |
| **Цена** | произвольные деревья диалога не выражаются; для ТЗ они и не нужны |

### 9. Обращения только по нажатию, флаг варианта — сигнал риска

| | |
|---|---|
| **Решение** | вариант опроса с флагом ставит сигнал в карточку, зону и дайджест. Обращение заводит нажатие «Описать проблему» или «Чат с HR» либо текст сотрудника. Сразу уходят только F0, F5, F9 и серьёзное без ветки |
| **Почему** | в прогоне сверки проблемный сотрудник получал 12 обращений, 5 из них автоматически поверх веток ТЗ. Так и в ТЗ: варианты дают кнопки «описать» и «связаться». После правила — 8 обращений, ровно по действиям |
| **Отвергли** | автоматическое обращение на каждый флаг |
| **Цена** | если сотрудник выбрал тревожный вариант, но не нажал «связаться», HR узнает из зоны риска и дайджеста, а не из очереди |

### 10. Жалобы мимо руководителя

| | |
|---|---|
| **Решение** | F0, F4, F5, F9, F10 руководителю не видны; F5 и F9 скрывают текст, F9 идёт в СБ |
| **Почему** | конфликт с руководителем не должен уходить этому руководителю. Это правило таблицы и кода, а не промпта |
| **Цена** | ролей в кабинете нет, поэтому скрытие держится на интерфейсе и выдаче API |

### 11. Распознавание голоса локально (T-one)

| | |
|---|---|
| **Решение** | голосовые распознаёт T-one (sherpa-onnx) на процессоре нашей машины; если MAX сам прислал расшифровку, берём её |
| **Почему** | звук не уходит наружу. 30 с речи — около 1 с; whisper small — 4,4 с, medium — 13,5 с при близком качестве. T-one правильно слышит «ГТП», whisper — нет |
| **Отвергли** | whisper; внешний сервис распознавания; эмоции по голосу (в ЕС запрещено на рабочем месте) |
| **Цена** | T-one пишет без пунктуации и цифр, уверенности не даёт. На живой речи в цеху не мерили. Вживую в MAX не проверено |

### 12. Снятый лимит подписи кнопки

| | |
|---|---|
| **Решение** | подписи кнопок из ТЗ сохраняются целиком; длиннее 24 символов — жёлтое замечание, публикацию не блокирует |
| **Почему** | лимит 18 символов пришёл из UX-спеки, но в MAX его нет: ограничение — 7 кнопок в ряд (dev.max.ru). Импорт резал подписи ТЗ |
| **Отвергли** | обрезку до 18 |
| **Цена** | длинная подпись может обрезаться на экране телефона самим MAX. Бот ставит две кнопки в ряд, только если обе не длиннее 16 символов |

### 13. Текст на «вы» и переписывание моделью

| | |
|---|---|
| **Решение** | у каждого текста два варианта: на «ты» и на «вы». ТЗ на «ты», вариант на «вы» и нейтральный род по кнопке HR готовит модель, код проверяет числа, ссылки, подстановки, «ты» и число, HR вычитывает по бейджу |
| **Почему** | главная находка e2e-прогона: сотрудник на «вы» получал «с тобой». Форму выбирает сотрудник сам |
| **Отвергли** | переписывать на лету при каждой отправке; дообучение модели |
| **Цена** | вычитка остаётся за HR; род модель убирает не везде (5 случаев остаются с замечанием) |

### 14. Дни от даты выхода, рабочие часы площадки

| | |
|---|---|
| **Решение** | шаги считаются в днях от D0, уходят в рабочие часы площадки, выходные переносятся, перенос даты выхода не дублирует шаги |
| **Почему** | так написано ТЗ; это отличает продукт от «воронки в минутах» обычных конструкторов ботов |
| **Цена** | рабочие дни и месяцы ТЗ пока приближены (рабочий = календарный, месяц = 30 дней), праздники и смены GTP не учтены |

### 15. Экспорт в Excel с листом расширений

| | |
|---|---|
| **Решение** | выгрузка в формате ТЗ плюс второй лист «Корсик — расширения» |
| **Почему** | HR привык к Excel; круговой путь доказывает, что конструктор выражает ТЗ целиком |
| **Цена** | при ручной правке строки на первом листе её расширения отбрасываются |

## Открытые решения за человеком

Из `08-night-report.md` и `checkpoint-2410.md`. По каждому — варианты и наша рекомендация.

### 1. П. 4.3.2: материалы заказчика уходили на нашу модель

Фрагменты ПВТР и тексты ТЗ обрабатывала T-lite на RunPod (замеры поиска, переписывание на «вы»).

| Вариант | Плюс | Минус |
|---|---|---|
| А. Спросить разрешение у кейсодержателя | честно и закрывает вопрос | могут отказать |
| Б. Дальше гонять материалы заказчика только без модели | безопасно формально | теряем пересказ и переписывание на настоящих данных |
| В. Ничего не делать, отвечать формулировкой | без усилий | риск вопроса жюри без готового ответа |

**Рекомендация:** А сейчас, а до ответа — Б для новых прогонов. На защите — формулировка 1 из `facts.md` §7.

### 2. Дата конца испытательного срока

В ТЗ — D+89. В прогоне это суббота, бот переносит на понедельник D+91, после конца срока.

| Вариант | Плюс | Минус |
|---|---|---|
| А. Брать дату конца ИС из карточки сотрудника (1С) | точно | нужно поле в карточке и логика якоря |
| Б. Оставить D+89, но переносить на **предыдущий** рабочий день | дёшево | всё равно не учитывает реальный срок |
| В. Оставить как есть | ничего не делать | итоговый опрос приходит после срока |

**Рекомендация:** спросить кейсодержателя; в коде — А в пилоте, Б как быстрая правка до защиты, если решите что-то менять.

### 3. Свободный вопрос во время живого диалога с HR

Пока обращение «в диалоге», любой текст сотрудника уходит в переписку, а не в поиск.

| Вариант | Плюс | Минус |
|---|---|---|
| А. Оставить так | HR видит всё, бот не встревает | простой вопрос «где столовая» ждёт ответа человека |
| Б. Отправлять вопросы в поиск, а в переписку — только ответы на HR | бот помогает параллельно | путаница, что кому адресовано |

**Рекомендация:** А. Это поведение предсказуемое, и ресерч закладывал его с самого начала (`01-architecture.md`: «пока обращение в HUMAN_ACTIVE, текст сотрудника идёт человеку»).

### 4. Материалы, которых нет в ТЗ

Маршруты, карты, PDF обеда, презентация, фото с праздников, образец резюме, 19 картинок. Сейчас бот пишет «Материал скоро добавим».

| Вариант | Плюс | Минус |
|---|---|---|
| А. Попросить у кейсодержателя | демо на их контенте | могут не успеть |
| Б. Нарисовать 2–3 демо-картинки самим | показать медиатеку живой | это не их материалы, пометить как демо |

**Рекомендация:** А и параллельно Б для показа медиатеки, с пометкой «демо».

### 5. Проверить голосовое с телефона

Неизвестно, отдаёт ли MAX файл голосового без токена бота и присылает ли расшифровку сам.

**Рекомендация:** отправить боту одно голосовое с телефона до защиты. Если не работает, бот честно ответит «Не разобрал голосовое, напишите текстом» — в демо голос тогда не показывать.
