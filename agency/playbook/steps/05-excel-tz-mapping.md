### 1.6 «Обязательный этап»

55 строк с «Да», 13 пустых. Пустые:
- письмо HR на e-mail;
- открытка D0 12:01;
- мини-резюме и адаптационный план («по отмашке рекрутера», 3 строки);
- весь блок корпоративных мероприятий D+10 для GrPP/Luzhniki (4);
- напоминание о встрече с рекрутером на D+44;
- блок 9 шкал конца ИС;
- 2 событийных правила.

Как это читаем: «обязательный» — ядро программы для всех. Такой шаг нельзя молча потерять. Если
бот подключён поздно, шаг попадает в сводку «Что вы пропустили». Интерактивный шаг (опрос или
вопрос с кнопками) без ответа получает напоминания через 24 и 48 ч, этого прямо требует строка с
правилом. Необязательный шаг — по ситуации: при опоздании пропускается, у новичка его можно
выключить.

### 1.8 Переменные и форма обращения

- **«Х»** — имя новичка, встречается в 15 строках. «Имя кандидата» — 1 раз, в e-mail.
- **Ты/вы**: у каждой строки ТЗ один текст. В 44 строках обращение на «ты». На «вы» написаны:
  - приветствие до выбора формы;
  - список документов из колонки J;
  - e-mail;
  - часть строки GTP о доступах (смешаны «ты» и «вы»);
  - оба блока шкал (D+14 и конец ИС).
- Тексты написаны в мужском роде: «пришел», «справился», «Готов/Готова». Переменной пола нет.

## 2. Соответствие ТЗ и конструктора

Легенда: ✅ поддерживается, 🟡 частично, ❌ нет.

### 2.1 Импорт сегодня

**Сегодня `POST /api/scenarios/import` на этом файле даёт 422 и 0 шагов.** Причин три, любая из них
блокирует импорт целиком:
1. Строка заголовка ищется по слову «когда», а в ТЗ колонка называется «Месяц/день/время
   информирования». Получаем `msgImportHeader`.
2. Если шапку исправить, `parseWhen` понимает только `D−3` / `D0 10:00` / `-3`. Ни одна из 61
   фраз ТЗ не разбирается, пустые «когда» (7 строк) — тоже ошибка.
3. Любая неразобранная строка отменяет весь файл. Отчёта «импортировано N, предупреждений M» нет.

Что совпадает уже сейчас:
- первый лист — нужный;
- «повод» → `title`, «текст» → `text_*`, «макет» → `kind`;
- «Опрос бота» → `survey` по умолчанию;
- «открытка» → `card`;
- теги GrPP/GTP/Luzhniki в любом регистре и через запятую → `sites`.

## 3. Спецификация доработок

Цель: файл ТЗ импортируется **целиком без ручной правки**, а сценарий из него в MAX ведёт себя
так, как описано в ТЗ. Приоритеты: **Must** — к показу 25.10, **Should** — после.

### 3.1 Импорт v2 (`scenario_xlsx.go`) — Must

1. **Поиск шапки по синонимам.** Нормализуем регистр и пробелы, ищем по вхождению:
   - `when`: «когда», «время информирования», «месяц/день»;
   - `sites`: «метка», «тег»;
   - `kind`: «макет», «форма»;
   - `required`: «обязательн»;
   - `media`: «изображ»;
   - `title`: «повод»;
   - `text`: «текст».

   Колонка без шапки справа от «текста» или «изображения» (J) идёт в `extra_text`. Безымянная
   колонка со словом «отмашк» (H) идёт в `condition`. Лист без шапки («Лист1») пропускается,
   берётся первый лист, где шапка нашлась. Колонку «№ п/п» не читаем.
2. **Разбор «когда»** в `{anchor, months, weeks, days, workdays, time}` по классам из 1.2:
   - «за N/день дня до выхода»; диапазон «2-3» → берём больший;
   - «в первый/второй/третий… рабочий день»: порядковые 1–10 → `workdays = N−1`;
   - «через N дней/недель [после выхода]»;
   - «первый день N-го месяца» → `months = N−1`;
   - «через N месяц(а/ев) [и M недели/дней]»;
   - «последний день ИС / испытат. срока» → `anchor = probation_end`;
   - время: `HH:MM` или `HH.MM` в любом месте строки;
   - хвост «для сотрудников офиса» / «для офисных» → `condition`;
   - «в случае варианта ответа «X»» → `trigger = answer` к последнему шагу с кнопкой X;
   - «если …» на уровне события → строка уходит в системные правила (3.7), шаг не создаётся.

   Старые форматы `D−3` и `D0 10:00` поддерживаем дальше.
3. **Пустое «когда» наследуется** из строки выше: это продолжение цепочки. Повод, площадки и
   условие тоже наследуются, если они пусты и строка — продолжение.
4. **Мягкий импорт.** Строки, которые не разобраны, не валят файл. Ответ — сценарий +
   `import_report: {rows, steps, warnings[{row, code, message}]}`. Коды предупреждений:
   - `media_missing` («Изображение 14» не загружено);
   - `alt_variants`;
   - `vy_copied`;
   - `question_without_options`;
   - `system_rule`;
   - `email_task`;
   - `unknown_when` (только если строка действительно не разобрана; такой шаг падает в D0 с
     пометкой).
5. **Плейсхолдеры:** отдельное слово «Х»/«X» → `{Имя}`; «Имя кандидата» → `{Имя}`.
6. **Варианты ответа из текста.** Блок «Варианты ответов:» (или нумерованный список в конце вопроса)
   + строки `1) …`, `- …`, `А) …` → `buttons`. Блок вырезается из текста. Подпись длиннее 18
   символов обрезается с предупреждением. Шаблон шага «готов к первому дню?» даёт 3 кнопки.
7. **Ветки «Если …:».** Блоки «Если ответили 1-2 / Если 3 / Если да / Если нет / Если ответ Б:»
   → дочерние шаги (3.2) с `trigger.on` = индексы кнопок. Текст после последней ветки, без
   условия, → дочерний шаг на все кнопки. «Опции для сотрудника: …» и «кнопку „связаться с
   рекрутером“» → кнопки эскалации на дочернем шаге (3.4).
8. **Вложения из текста.** Строка `# Приложить X` / `#X` / `+ОТКРЫТКА` вырезается и превращается
   в медиа-ссылку по имени: «пдф-ку с перечнем…» → «PDF: где пообедать (<площадка>)», открытка →
   имя из колонки I. URL в тексте с пометкой «Приложить ссылку» превращается в кнопку
   `link:` «Открыть справочник».
9. **Колонка I** → `media: [{name}]`. Если имени нет в медиатеке, создаётся пустая запись
   `status: missing` (3.3). «ФОТО» → галерея (`gallery: true`).
10. **Колонка G** → `required: true`, если там «да» в любом регистре.
11. **Ты/вы.** Текст ТЗ кладём в ту форму, в которой он написан (детектор по местоимениям
    ты/тебя/твой против вы/вас/ваш). Вторую форму пока копируем с предупреждением `vy_copied`. Кабинет
    показывает бейдж «нужен вариант на вы». Should: черновик второй формы генерирует LLM (T-lite),
    HR вычитывает.

### 3.2 Ветки и цепочки — Must

Модель: **дочерний шаг с триггером по ответу.** Отдельную «вложенную реплику» внутри кнопки не
вводим: так один механизм закрывает и «текст по кнопке», и «кнопка → строки с PDF по площадкам», и
реакции на ответы опроса.

```json
"trigger": {"type": "time"}                                    // по умолчанию, как сейчас
"trigger": {"type": "answer", "parent_id": "uuid",
            "on": [0, 1]}                                      // индексы кнопок родителя
"trigger": {"type": "answer", "parent_id": "uuid",
            "on_survey": {"q": 0, "options": [1, 2]}}          // вариант вопроса опроса
"trigger": {"type": "answer", "parent_id": "uuid",
            "on_survey": {"q": 2, "below": 8}}                 // оценка ниже порога
```

- Поле `trigger` jsonb в `ScenarioStep` и в снимке версии. Если поля нет, шаг считается `time`.
- У дочернего шага `day_offset`/`time` не используются. Он уходит сразу после нажатия: через
  pacer, с паузой `packGap`, в пределах лимита 2 сообщения в секунду. Площадки фильтруются так же,
  как у шага по времени (`AppliesTo`): три строки «PDF обеда» по площадкам — три дочерних шага с
  разными `sites`.
- Несколько дочерних шагов на один ответ — это цепочка, порядок по `position`. Дочерний шаг
  может сам иметь кнопки и детей. Глубину ограничиваем тремя, в ТЗ максимум 2.
- Событие таймлайна для дочернего шага создаётся при нажатии: `scheduled_events` с `parent_event_id`
  и `fire_at = now`. В траектории новичка видно, какая ветка сработала. Идемпотентность — по
  `(parent_event_id, step_id)`, повторное нажатие дубля не даёт.
- Текущее поведение «сообщение правится в ✅ <подпись>» оставляем: ответ видно, кнопки
  исчезают.
- Захардкоженная «Чего-то нет» → причины → F2 остаётся частным случаем. Позже её можно выразить
  как дочерний шаг с кнопками-причинами и `action: ticket:hr:F2`.
- Валидатор публикации (кнопка «Проверить» из UX 3.5) ловит три ошибки:
  - `parent_id` указывает на несуществующий шаг;
  - `on` выходит за число кнопок;
  - есть цикл.

  Отдельно — предупреждение, если у кнопки нет ветки, а в ТЗ она была.
- **Кабинет.** В правой панели шага, в разделе «Ветки по ответу» (UX 3.5), у каждой кнопки есть
  «+ Ответ на эту кнопку» (создаёт дочерний шаг `text`) и список дочерних шагов со ссылкой «открыть».
  В виде «Таблица» дочерние шаги идут с отступом под родителем, вместо дня — «↳ по ответу
  „Да“». В «Таймлайне» у родителя бейдж «ветки: N». Машина времени отправляет родителя.
  Ветки срабатывают от нажатий в тестовом диалоге.

### 3.3 Медиатека и вложения — Must

ТЗ ссылается на медиа **по имени** («Изображение 14»), а самих файлов в xlsx нет. Значит, нужна
библиотека с привязкой по имени.

- Таблица `media`. Поля:
  - `id`;
  - `name` — уникальный ключ, например «Изображение 14»;
  - `kind` (`image|file`);
  - `filename`, `mime`, `size`, `sha256`;
  - `path` — диск сервера, том docker;
  - `status` (`missing|ready`);
  - `max_token` — кэш токена загрузки;
  - `max_token_at`;
  - `updated_by`, `updated_at`.
- Поле шага `media: [{"media_id":"uuid","name":"Изображение 14"}]` и `gallery: bool`. Имя
  сохраняем рядом с id, чтобы импорт создал ссылку до загрузки файла.
- **Рендер в MAX** (по `deep-research` и `a_core_stack.md`):
  - `image`: до 12 штук в одном сообщении вместе с текстом и клавиатурой. Можно передать
    внешним `url` без загрузки. Мы всё равно загружаем через `POST /uploads?type=image` и
    кэшируем токен: на стенде нет публичного https для картинок, а повторная отправка
    по токену дешевле;
  - `file` (PDF): только загрузка `POST /uploads?type=file` → токен; **одно** вложение на сообщение
    плюс клавиатура. Если у шага и картинка, и файл, уходит два сообщения подряд: сначала картинка
    с текстом, потом файл с кнопками;
  - ретрай `attachment.not.ready` уже есть в SDK. Протухший токен → перезагрузка файла,
    `max_token` обновляется;
  - шаг с `media.status = missing` уходит без вложения, в журнал пишется предупреждение. HR видит
    «⚠ медиа не загружено» в списке шагов и в «Проверить».
- `stepMessage` заполняет `OutMessage.Attachments`. `FakeJournal` уже показывает вложения в dev-чате.
- **Кабинет.**
  - Вкладка «Медиа» в «Сценариях»: список имён, у пустых — бейдж «нужно загрузить», статус,
    превью, «Загрузить/Заменить» (multipart). После импорта ТЗ там 19 имён картинок и ~5
    PDF-плейсхолдеров.
  - В панели шага: «Картинка/файл: [выбор из медиатеки ▾] [Загрузить]», как в макете UX 3.5.
- API:
  - `GET /api/media`;
  - `POST /api/media` (multipart `file`, `name`);
  - `PUT /api/media/{id}` (замена файла);
  - `GET /api/media/{id}/content` (превью в кабинете).
- Персональный файл — адаптационный план, свой у каждого новичка. Это не медиатека, а файл в
  карточке новичка: `media` шага `{"personal":"adaptation_plan"}`. Нет файла → дочерняя ветка
  «Плана ещё нет» из UX 2.3. **Should.**

### 3.4 Кнопки эскалации — Must

Расширяем `buttons[].action`. Старые значения не меняются:

| action | Что делает |
|---|---|
| `human:hr` / `human:recruiter` | «Связаться с HR / рекрутером»: обращение v2 с маршрутом. Переписка идёт через бота (HUMAN_ACTIVE). Прямую ссылку на профиль рекрутера (`max://user/<id>`) не используем, пока она не проверена (UX 5, п. 3) |
| `ticket:hr` / `ticket:recruiter` | «Передать проблему через Корсика»: бот просит описать проблему одним сообщением. Текст проходит детектор флагов, потом создаётся обращение (в опросах механика `write` уже есть) |
| `ticket:<route>:<F-код>` | то же с заранее известной категорией (например, доступы F2) |

Импорт: «связаться с рекрутером» → `human:recruiter`; «передать проблему в отдел подбора через
Корсика» → `ticket:recruiter`; «связаться с HR», «/HR» → `human:hr`. В кабинете поле action
заменяется селектом:
- «Записать ответ»;
- «Ссылка»;
- «Связаться с …»;
- «Передать проблему через Корсика»;
- «Пропустить».

### 3.5 Опросы — Must (разбор и рендер) / Should (ветки)

Модель становится повопросной, старые опросы читаются как раньше:

```json
"survey": {"scale": "1-10", "threshold": 8,            // значения по умолчанию для вопросов
  "questions": [
    {"text": "…", "type": "scale", "scale": "1-10", "threshold": 8,
     "anchors": ["недоступен", "всегда доступен"], "comment": "below"},
    {"text": "…", "type": "yesno", "comment": "on_no"},
    {"text": "…", "type": "choice", "options": ["…"], "other": true},
    {"text": "…", "type": "multi",  "options": ["…"]},
    {"text": "…", "type": "text"}
  ]}
```

- **Must.** Импорт режет текст опроса на вопросы по «Вопрос N:» и по нумерации `1) / 1. /
  1.\t`. Варианты берутся из `А) / - / •`. Тип вопроса определяется по прозе ТЗ:
  - «шкала 1 … 10 …» → `scale` 1–10 с подписями краёв;
  - «(да/нет)» → `yesno`;
  - «ниже 8» → `threshold: 8`;
  - «поле для комментария» → `comment`;
  - «несколько вариантов» → `multi`;
  - «свой вариант / другое» → `other`;
  - «Открытый вопрос» → `text`.

  Строки без «когда» после «Опрос бота» склеиваются в один опрос. Блок 9 шкал на конце ИС
  приклеивается к опросу конца ИС.
- **Must.** Рендер в MAX — «живое сообщение» (UX 2.4), разные шкалы в одном опросе:
  - кнопки строятся по `type` вопроса;
  - `multi` — кнопки-переключатели «✓ …» + «Готово»;
  - `other` и `text` — бот ждёт следующий текст новичка как ответ на вопрос (механика `write`
    уже есть), а не как вопрос в RAG.
- **Should.** Реакции на варианты («Если ответ Б: …», блок «ОТВЕТЫ:» в D+51) импортируются как
  дочерние шаги с `on_survey` (3.2). Если до показа не успеваем, импорт кладёт их текстом в
  предупреждение `survey_branch_skipped`, а в сиде они уже заданы руками.

### 3.6 Условия — Should

`condition` перестаёт быть свободной строкой:

```json
"condition": {"manual": "mini_resume"}        // «по отмашке рекрутера»
"condition": {"tags_any": ["office"]}         // «для офисных сотрудников»
```

- У новичка появляются `tags` (в ТЗ нужен только `office|production`; по умолчанию GTP →
  `production`, остальные площадки → `office`, в карточке можно поменять) и `switches` —
  включённые ручные шаги.
- Условие проверяется **в момент отправки**, а не при запуске (UX 3.5). Не прошёл → событие
  `skipped` с причиной.
- Шаг `manual` создаётся в статусе `held`. В траектории новичка у него переключатель «Включить
  (по отмашке рекрутера)». Включили до срока — уйдёт по расписанию, после срока — сразу.
- Для показа можно ограничиться `manual`: оба шага ТЗ с «отмашкой» как раз демонстрационные.

### 3.7 Обязательность и системные правила — Must (поле) / Should (напоминания)

- `required: bool` в шаге (Must, импорт из G).
- **Should.** Планировщик напоминает по интерактивному обязательному шагу (опрос или кнопки), если
  ответа нет: +24 ч и +48 ч, в рабочие часы. Текст и картинка (№12) берутся из системного правила
  ТЗ. После двух напоминаний — `unanswered` и сигнал в карточке, без эскалации (UX 2.3). У
  необязательного шага напоминаний нет, и при позднем подключении он пропускается. Обязательный
  попадает в «Что вы пропустили».
- Системные правила (две строки-события) импортируются в настройки сценария, а не в шаги:
  `scenario.rules.survey_reminder {text, media}` и `scenario.rules.fallback {text, media}`. Для
  fallback наш RAG-отказ остаётся основным, текст ТЗ — его вариант.

### 3.8 Время — Should

Поле `when: {"anchor":"start|probation_end","months":0,"weeks":0,"days":0,"workdays":false}`.
`day_offset` остаётся вычисляемым, его используют таймлайн, этапы и машина времени.
- `workdays: true` пропускает выходные: «третий рабочий день» с выходом в пятницу — это вторник.
- Месяцы считаются календарно: старт 31.01 + 1 мес. → последний день февраля.
- `probation_end` берётся из карточки новичка (новое поле, по умолчанию старт + 3 мес. − 1 день).

Для показа хватит приближения импорта: рабочие дни как календарные, 1 мес. = 30 дней, конец ИС =
D+89. Неточность видна в предупреждениях.

### 3.9 Прочее — Should

- `format: "markdown"` на шаге: гиперссылка на слове, жирная первая строка (UX 2.2).
- Переменная рода `{готов|готова}` и поле пола в карточке.
- Тексты длиннее 500 символов кабинет помечает «длинное — разбить?».

### 3.10 Итог по приоритетам и трудоёмкость

Оценка в часах одного разработчика (агентом примерно так же), с тестами и правками
`api_contract.md`:

| # | Что | Приоритет | Back | Front | Итого |
|---|---|---|---|---|---|
| 1 | Импорт v2: шапка, «когда», продолжения, мягкий отчёт, Х, G, I, J, варианты из текста | Must | 5–6 | 1 (отчёт импорта) | **6–7** |
| 2 | Ветки: `trigger` по кнопке, дочерние события, рендер, валидатор, импорт «Если…» | Must | 5–6 | 3 | **8–9** |
| 3 | Медиатека + вложения в MAX (upload, кэш токена, 1 файл/сообщение) | Must | 3–4 | 3 | **6–7** |
| 4 | Кнопки эскалации `human:*` / `ticket:*` | Must | 2 | 0,5 | **2–3** |
| 5 | Опросы: разбор ТЗ, повопросные типы, multi/other/text в рендере | Must | 5–6 | 2 | **7–8** |
| | **Must всего** | | | | **≈ 29–34 ч** |
| 6 | Реакции на ответы опроса (`on_survey`) | Should | 2 | 1 | 3 |
| 7 | Условия `manual` + `tags`, переключатель в траектории | Should | 3 | 1,5 | 4–5 |
| 8 | Обязательность → напоминания 24/48 ч, правила сценария | Should | 3 | 0,5 | 3–4 |
| 9 | `when` с рабочими днями, месяцами, концом ИС | Should | 3 | 1 | 4 |
| 10 | Вторая форма ты/вы через LLM, род, markdown | Should | 3 | 1 | 4 |
| | **Should всего** | | | | **≈ 18–20 ч** |

Must целиком (≈ 30 ч) к показу 25.10 не помещается. **Минимальный срез для демо (≈ 12–14 ч)**:
1. импорт v2 без разбора опросов: опрос → шаг-опрос с вопросами из «Вопрос N» и вариантами, без
   смешанных шкал;
2. медиатека с загрузкой по имени и отправкой image/file;
3. ветки «кнопка → дочерние шаги» с импортом «Если…» и «В случае варианта ответа»;
4. `human:recruiter`.

Этого хватает, чтобы на показе загрузить настоящий Excel заказчика и получить работающий сценарий
с картинками, PDF по площадкам и ветками. Сложные опросы на показе — из сида (там они собраны
руками).
