# RAG-сервис Корсика

Отвечает новичку по регламентам компании и всегда указывает пункт-источник. Если источника
нет, сервис отказывает и просит позвать человека. По умолчанию работает без GPU и без моделей:
BM25 и экстрактивный ответ. Dense-поиск `BAAI/bge-m3` и реранкер `BAAI/bge-reranker-v2-m3`
включаются флагами и работают на CPU. LLM подключается через переменные окружения.

Контракт `GET /health`, `POST /ask`, `POST /flags`, `POST /transcribe` (голосовые, раздел
«Голос») задан в `agency/system/api_contract.md`.
Эндпоинты загрузки `POST /documents` и `GET /documents` описаны ниже, в контракт их перенесёт
оркестратор.

> В `testdata/corpus/` лежит **синтетический** регламент из 15 пунктов. Его составили вручную
> для тестов, это не копия ПВТР ПОЛИПЛАСТИК. В образе он стоит корпусом по умолчанию.
> Настоящие документы заказчика лежат локально в `corpus-real/` (в `.gitignore` и
> `.dockerignore`, коммерческая тайна). Как их подключить — раздел «Реальный корпус».

## Конвейер `/ask`

```
route → expand (synonyms.yaml) → retrieve (BM25 ⊕ bge-m3, RRF k=60, top-20) → rerank (bge-reranker, top-5) → gate
      → [gate не прошёл: rewrite (LLM, 1–3 формулировки) → retrieve + rerank → согласие → gate]
      → generate → verify → проверки ответа
```

| Шаг | Как работает |
|---|---|
| route (`routing.py`) | regex: зарплата конкретного человека, увольнение, конфликт, здоровье, «игнорируй инструкции», «как обойти». Ответ `routed_topic`, LLM не вызывается |
| expand (`query_expand.py`) | словарь разговорной лексики `synonyms.yaml`: «проспал», «покурить», «откат», «кусками» → термины регламента дописываются к вопросу. `RAG_SYNONYMS=rerank` (по умолчанию): расширенный вопрос идёт в BM25 и bge-m3, реранкер скорит пункт и исходным, и расширенным вопросом, берётся максимум; `retrieve` — только в поиск; `off` — выключено |
| retrieve (`retrieval.py`) | `RAG_RETRIEVER=bm25`: BM25Okapi по леммам `pymorphy3`, номера пунктов (`3.2.1`) — отдельные токены. `RAG_RETRIEVER=hybrid`: BM25 + bge-m3 (cosine по L2-нормированным эмбеддингам) через RRF k=60, top-20 |
| rerank | `RAG_RERANKER=none`: без изменений. `RAG_RERANKER=bge`: bge-reranker-v2-m3 скорит **каждый пункт** первых `RAG_RERANK_TOP` (8) кандидатов парой (вопрос, «раздел. текст пункта»), скор чанка = максимум по пунктам, top-5 |
| gate | без реранкера: доля слов вопроса, найденных в чанке, взвешенная по IDF, порог 0.5. С реранкером: sigmoid логита лучшего пункта, порог **0.2** (калибровка на реальном корпусе, раздел «Реальный корпус»; на синтетике был 0.1). `RAG_GATE_THRESHOLD` переопределяет оба |
| rewrite (`rewrite.py`) | только если gate не прошёл и задан `LLM_BASE_URL` (`RAG_REWRITE=1`). LLM по промпту `prompts/query-rewrite.md` переписывает вопрос в 1–3 формулировки языком регламента (бюджет `RAG_REWRITE_TIMEOUT`, 3 с); формулировки с новыми числами и попавшие в маршрут отбрасываются. По каждой — поиск, `RAG_REWRITE_RERANK_TOP` (4) кандидата в реранкер. **Согласие**: пункт засчитывается, только если он первый ещё у одного запроса (исходный вопрос или другая формулировка). Gate тот же. Пункт, найденный так, отдаётся **только если его подтвердила LLM** на исходный вопрос (для legal/security тоже, но ответ — цитата); таймаут, отказ модели или число не из пункта — отказ `below_threshold`. Подробности — «Реальный корпус» |
| generate (`llm.py`) | если `LLM_BASE_URL` задан — OpenAI-совместимый `/chat/completions` по промпту rag-answer v2 (ниже) со structured outputs. Иначе, или если LLM недоступен, ответил не JSON, не по схеме или упёрся в `max_tokens`, — дословная цитата лучшего пункта (с реранкером — того, который он выбрал) |
| verify (`verify.py`) | каждый `clause_id` есть среди найденных пунктов, `quote` входит в текст **этого** пункта после нормализации, в цитате не меньше 3 слов. Хоть один источник не прошёл — `needs_escalation=true` |
| проверки ответа LLM (`verify.py`) | только для ответа LLM, экстрактивная цитата их не проходит: (1) каждое число `answer` есть в тексте процитированных пунктов, иначе `needs_escalation=true`; (2) `answer` ≤ 700 символов, длиннее — обрезка по концу предложения, а если не влезает даже первое предложение — `needs_escalation=true`. Подробности ниже |

Темы `legal` и `security` (взыскания, коммерческая тайна, пропуска, охрана) отвечаются только
цитатой, LLM их не пересказывает.

Значения `abstain_reason`:
- `routed_topic` — вопрос не для бота;
- `below_threshold` — что-то нашлось, но gate не пропустил;
- `no_source` — ничего не нашлось, LLM сам отказался или проверка цитат не прошла.

У dense-попаданий собственного gate-скора нет (0): косинус bi-encoder'а меряет близость темы,
а не то, отвечает ли пункт на вопрос. Поэтому `hybrid` без реранкера гейтится лексическим
покрытием BM25 и перефразы по-прежнему отклоняет. Рабочая конфигурация — `hybrid` + `bge`.

## Генерация LLM (промпт rag-answer v2)

Источник истины — `agency/prompts/rag-answer.md`. В Docker-контекст `services/rag` каталог
`agency/` не попадает, поэтому сервис читает его копию `prompts/rag-answer.md`. Из markdown
берутся блоки A (system prompt), B (шаблон user), C (JSON-схема), D (6 few-shot пар) и строка
`Версия: **v2**`. Код ждёт версию `PROMPT_VERSION = "v2"` и падает на старте, если копия другой
версии или блок не разобрался. `tests/test_llm.py` сравнивает копию с источником по версии и
блокам A–D. После правки промпта: `cp agency/prompts/rag-answer.md services/rag/prompts/` и,
если поднялась версия, `PROMPT_VERSION` в `llm.py`.

Запрос: `system` (с подстановкой `{address_form}` → «ты»/«вы» и `{site}` → площадка или
«не указана») → 6 пар user/assistant few-shot → user с `<doc …>` и `<question>…</question>`.
Теги `</question>` из вопроса вырезаются, `</doc>` в тексте пункта экранируется. В каждом
запросе `temperature`, `presence_penalty`, `top_p`, `max_tokens=768`.

Схема: `sources` → `answer` → `confidence` → `needs_escalation`, `maxItems: 3`,
`additionalProperties: false`. Порядок свойств сохраняется в теле запроса (тест), сервер с
xgrammar генерирует поля в порядке схемы — это утверждение промпта, на нашем vLLM не проверено.

`LLM_STRUCTURED` — как передать схему:

| Значение | Что уходит в теле запроса | Статус |
|---|---|---|
| `json_schema` (по умолчанию) | `response_format: {"type": "json_schema", "json_schema": {"name": "rag_answer", "schema": …}}` | OpenAI-формат. В текущей документации vLLM (docs.vllm.ai, stable) сервер переводит его в `structured_outputs.json` |
| `structured_outputs` | `structured_outputs: {"json": …}` на верхнем уровне тела (в openai-SDK это `extra_body`) | vLLM-специфичный путь; `guided_json` удалён в vLLM 0.12 |
| `none` | ничего, схема только в тексте промпта | Ollama и серверы без structured outputs |

На каком vLLM стоит под, я не проверял: доступа к серверу не было, документация смотрелась
по ветке stable, а не по тегу 0.31. Оба пути есть в stable-документации. Если сервер отвечает
400 на `response_format`, в eval это видно как `llm-fallback` 100% с исходом
`fallback:HTTPStatusError` — тогда перезапустить с `LLM_STRUCTURED=structured_outputs`.

`address_form` в `/ask`: `ty` | `vy` | `null`, необязательное, по умолчанию «вы».

### Проверки ответа LLM кодом

- **Числа.** Каждое число из `answer` (`25`, `20:00`, `1,5`) должно быть в тексте одного из
  процитированных пунктов, иначе отказ (`abstain_reason=no_source`). Разделители `.,:`
  приравнены, а часть составного числа допустима: «в 20 часов» проходит по «20:00».
  Разрешены только процитированные пункты, а не весь чанк: чанк «3.1+3.2» иначе пропустил бы
  «доплата 40%» к ответу про 3.2 из-за «40 часов» в 3.1. Числа из вопроса не разрешены, иначе
  инъекция «аванс 1-го числа?» стала бы «фактом». Числа словами («три дня») не проверяются.
  Почему отказ, а не `confidence=low`: бот показывает ответ при любой уверенности, а неверный
  срок или сумма хуже эскалации к человеку.
- **Длина ≤ 700.** Длиннее — обрезка по последнему концу предложения до 700 символов,
  `confidence` high → medium. Если даже первое предложение длиннее 700 — отказ. Почему
  обрезка: по промпту первое предложение — прямой ответ, дальше условия, а 8B плохо считает
  символы (риск из `agency/prompts/README.md`). Отказ на каждом длинном ответе превратил бы
  ошибку счёта в потерю ответа. Посреди фразы не режем. Цена обрезки — может пропасть условие
  из хвоста, но источник с цитатой бот показывает всегда. Числа проверяются по полному тексту
  до обрезки.
- Экстрактивный ответ (дословный пункт) этих проверок не проходит: он и так дословный, длину
  не меняем.

## Модели

| Модель | Параметров | Веса на диске (FP32 safetensors) | RAM процесса с обеими моделями |
|---|---|---|---|
| `BAAI/bge-m3` | ~568M | 2.27 ГБ | ~1.9 ГБ (замер `docker stats`, обе модели загружены) |
| `BAAI/bge-reranker-v2-m3` | ~568M | 2.27 ГБ | |

- Веса скачиваются с Hugging Face при первом старте с флагами в кэш `HF_HOME`. Локально это
  `services/rag/.cache/` (`run.sh` выставляет сам, каталог в `.gitignore` и `.dockerignore`).
  В образ они не попадают: в контейнере `HF_HOME=/app/.cache`, туда монтируется тот же каталог.
- Сейчас кэш занимает 6.4 ГБ: для bge-m3 `transformers` 5 скачал и `pytorch_model.bin`, и
  `model.safetensors` из ветки конвертации (2.27 ГБ дубль). Первое скачивание шло ~9 минут.
- Работают на CPU в FP32. Окно обрезано до 1024 токенов (`DENSE_MAX_TOKENS`,
  `RERANK_MAX_TOKENS`): чанк не длиннее 400 слов, а полное окно bge-m3 8192 только замедляет CPU.
- Старт с обеими моделями из кэша (загрузка + эмбеддинги корпуса): 6–12 с на Apple M4, в
  зависимости от того, прогрет ли дисковый кэш ОС. Эмбеддинг чанка (~50 слов) ~0.14 с,
  эмбеддинг вопроса ~80 мс.
- Эмбеддинги чанков кэшируются по тексту, поэтому после загрузки документа считаются только
  новые чанки. Пересборка BM25 — миллисекунды.

Предзагрузка без старта сервиса:

```bash
HF_HOME=$PWD/.cache .venv/bin/python -c "from sentence_transformers import SentenceTransformer, CrossEncoder; SentenceTransformer('BAAI/bge-m3'); CrossEncoder('BAAI/bge-reranker-v2-m3')"
```

Когда кэш уже заполнен, `HF_HUB_OFFLINE=1` выключает обращения к Hub на старте.

## Чанкинг (`chunker.py`)

Вход: файлы из `RAG_CORPUS_DIR` — каталог или несколько через запятую
(`testdata/corpus,corpus-real`). `*.txt` и `*.md` в UTF-8 идут в клаузный чанкер, `*.pdf`,
`*.pptx`, `*.xlsx` — через `parsers.py`, как при загрузке. Lock-файлы `~$…` и скрытые файлы
пропускаются. PDF-скан распознаётся на каждом старте (~45 с на 23 страницы), поэтому скан лучше
один раз выгрузить в md (`python parsers.py export`, ниже). Индекс собирается в памяти на старте.

```
---
doc: ПВТР            ← имя документа в sources[].doc (иначе имя файла)
title: ...
version: ...
---
--- стр. 3 ---        ← номер страницы (или символ \f)
6. Оплата труда       ← раздел
6.1. Текст пункта...  ← пункт: 1–2 цифры, точка, до 3 цифр (6.1, 6.1.3, 6.10.24)
продолжение пункта    ← строки без номера приклеиваются к пункту
```

Один пункт — один чанк. Пункт короче 50 слов склеивается с соседом, у которого тот же родитель
(родитель `6.1.3` — это `6.1`, родитель `6.1` — раздел `6`). Склеиваются только соседи по порядку,
чанк не растёт больше 250 слов (было 400: на ПВТР склейка давала чанки на 12 пунктов и 380 слов).
В поисковый текст чанка дописывается заголовок «документ, раздел, пункты». Цитаты проверяются по
чистому тексту пункта. Текст до первого пункта раздела не индексируется.

Правила, добавленные под настоящий ПВТР (тесты в `tests/test_chunker.py`):
- **Подраздел.** Пункт `6.1. Порядок приема работников`, за которым идут `6.1.N`, если он не
  длиннее 14 слов и не кончается на `.:;,`, — заголовок: в индекс не идёт, его текст становится
  разделом подпунктов. Пункт «4.1 … 28 календарных дней.» с подпунктом 4.1.1 остаётся пунктом.
- **Раздел без пунктов** (термины, сокращения, нормативные ссылки) — один пункт с номером раздела
  (`3`). Повторы номера из оглавления отбрасываются: берётся самый длинный текст.
- **Номер без пробела** после OCR (`6.3.11.В случае`) — пункт. Шифр документа `3.1107`
  (так OCR читает «П 3.11-07» в шапке) — не пункт.
- **Длинный пункт** (> 200 слов: перечень обязанностей на 560 слов) режется на части `6.4.2/1`,
  `6.4.2/2` … по ~120 слов. Граница — тире пункта перечня после `;:.`, иначе конец предложения.
  Окно реранкера и bge-m3 — 1024 токена, без нарезки хвост перечня (курение, пропускной режим)
  не попадал в скор. Текст части дословный; вводная фраза («Работник обязан») дописывается в
  раздел частей со второй. В `sources[].clause_id` уходит `6.4.2/5`, verify и проверка чисел
  работают с частью как с пунктом.

## Загрузка документов HR (`parsers.py`, `documents.py`)

`POST /documents` — `multipart/form-data`:

| Поле | Обязательно | |
|---|---|---|
| `file` | да | `.pdf`, `.pptx`, `.xlsx`, `.txt`, `.md`, не больше `RAG_MAX_UPLOAD_MB` (25) |
| `doc` | нет | имя документа для `sources[].doc`, до 200 символов. Иначе имя файла без расширения (для md/txt — `doc` из front-matter) |

→ 200
```json
{"doc_id": "6ec3792d15de4816", "chunks": 2, "clauses": 2, "low_confidence_pages": [3]}
```

- `doc_id` — первые 16 hex от sha256(имя документа + байты файла).
- `low_confidence_pages` — страницы (для PPTX — номера слайдов), которые нужно вычитать:
  OCR со средней уверенностью Tesseract ниже 70, скан без установленного tesseract, пустой
  слайд.
- Документ с тем же `doc` заменяет предыдущий целиком, в том числе корпусный: две версии одного
  регламента в индексе дали бы цитаты из устаревшей.
- Ошибки: 415 — формат не поддерживается; 422 — пустой или битый файл, не UTF-8, текст не найден;
  413 — файл больше лимита. Тело ошибки — стандартное FastAPI `{"detail": "..."}` без содержимого
  файла.
- Индекс пересобирается синхронно в запросе. С `hybrid` каждый новый чанк проходит через bge-m3
  (на M4 ~0.14 с на чанк в 50 слов, длинные чанки дольше), для регламента на сотню пунктов это
  десятки секунд.
- Хранится в памяти процесса. После рестарта остаётся только корпус из `RAG_CORPUS_DIR`.

`GET /documents` → `{"items": [...], "total": N}`, элемент:

```json
{"doc_id": "…", "doc": "ПВТР-синтетика", "filename": "pvtr.pdf | null", "kind": "corpus|pdf|pptx|xlsx|text",
 "source": "corpus|upload", "chunks": 10, "clauses": 15, "low_confidence_pages": [], "uploaded_at": "2026-10-23T20:36:48+00:00"}
```

Как разбирается каждый формат:

| Формат | Разбор | Чанк | `clause_id` / `page` |
|---|---|---|---|
| PDF с текстовым слоем | `pypdfium2`, постранично | пункт, как в корпусе; если номеров `N.N` нет — страница | `6.1` / номер страницы; без пунктов `стр. 3` |
| PDF-скан | страница, где в текстовом слое меньше 30 символов, рендерится в 300 dpi и идёт в `tesseract -l rus+eng --psm 4` (TSV, уверенность по словам) | так же | так же |
| PPTX | `python-pptx`: заголовок, текст фигур и групп, таблицы строками `a \| b`, **текст SmartArt** (часть `diagramData`, python-pptx её не отдаёт), заметки докладчика | слайд | `слайд 3` / номер слайда, `section` = заголовок слайда |
| XLSX | `openpyxl`, первая непустая строка листа — заголовки | строка «Заголовок: значение \| …» | `строка 5` / `null`; при нескольких листах `doc` = «имя / лист» |
| TXT, MD | как корпус | пункт | как корпус |

Пост-обработка текста PDF (и OCR, и текстового слоя):
- колонтитулы: строки из первых и последних двух строк страницы, которые с точностью до цифр
  повторяются на половине страниц и больше, плюс строки-номера страниц («- 3 -», «Стр. 2 из 23»).
  Строку, похожую на пункт или заголовок раздела, колонтитулом не считаем;
- шапка-штамп скана (5–8 строк: организация, шифр, «Лист N», «Листов M», название), которую OCR
  каждый раз читает по-разному: словарь шапки — слова из первых 8 строк, встречающиеся на половине
  страниц и больше; срезается всё до последней короткой (≤ 8 слов) строки, где таких слов не меньше
  половины. Блок заканчивается на первом пункте или разделе;
- переносы: «трудо-\nвого» → «трудового», мягкие переносы удаляются;
- омоглифы: латинские буквы внутри кириллического слова → кириллица («пpопуск»). Слова целиком
  латиницей (MAX, Wi-Fi) не трогаются;
- номера пунктов: «6,1.» → «6.1.», «6.1 .» → «6.1.». «3. 15 минут» не трогаем: от «3.15» это
  не отличить.

Выгрузка скана в md корпуса (OCR один раз, текст можно вычитать глазами). В stdout — только
уверенность по страницам и счётчики, текст документа не печатается:

```bash
.venv/bin/python parsers.py export путь/к/скану.pdf --doc "ПВТР П 3.11-07" -o corpus-real/pvtr.md
```

OCR в Docker: `tesseract-ocr` и `tesseract-ocr-rus` ставятся в образе. Локально tesseract
нужен в системе (`tesseract --list-langs` должен показать `rus` и `eng`). Без него сканы не
распознаются, а их страницы возвращаются в `low_confidence_pages`.

`eval/golden.csv`: 40 вопросов по синтетическому регламенту, колонки `question,
expected_clause_ids, is_trap, topic, kind`. Колонку `kind` я добавил сверх заданных четырёх,
чтобы считать метрики отдельно для `literal` и `paraphrase`.

| kind | Сколько | Что это |
|---|---|---|
| `literal` | 13 | формулировки близки к тексту пункта |
| `paraphrase` | 16 | разговорный перефраз без ключевых слов пункта («получка», «посеял бейджик», «каникулы»). Служебные слова и часть темы («офис», «пропуск») могут совпадать |

### Оценка с LLM

Конфигурация `final+llm` — это `final` плюс генерация по промпту v2 и проверки ответа. Она
включается, только если задан `LLM_BASE_URL`, иначе пропускается с сообщением в stderr. Адрес,
модель и ключ берутся из окружения (`LLM_BASE_URL` с `/v1`, `LLM_API_KEY`, `LLM_MODEL`,
`LLM_STRUCTURED`). Eval печатает модель и `key=set|none`, адрес и ключ не печатает.

Команда для пода (переменные уже экспортированы в shell, значения в команде не пишутся):

```bash
cd services/rag
: "${LLM_BASE_URL:?LLM_BASE_URL не задан}" "${LLM_MODEL:?LLM_MODEL не задан}"
HF_HUB_OFFLINE=1 ./run.sh eval --configs final,final+llm --presence-penalty 1.0,0.3 -v \
  --json "${TMPDIR:-/tmp}/rag-eval-llm.json" 2>&1 | tee "${TMPDIR:-/tmp}/rag-eval-llm.log"
```

- `--presence-penalty 1.0,0.3` — A/B из `agency/prompts/README.md`: две колонки
  `final+llm pp=1` и `final+llm pp=0.3`. Без флага — один прогон со значением из
  `LLM_PRESENCE_PENALTY` (1.0).
- Если vLLM не принимает `response_format`, добавить перед командой
  `LLM_STRUCTURED=structured_outputs`.
- Время: 40 вопросов на конфигурацию, на каждый — реранкер на CPU (~1.5 с на M4) плюс вызов
  LLM. Плюс загрузка bge-моделей на каждую конфигурацию (6–12 с из кэша).

Метрики LLM в таблице:
- «LLM: ответ прошёл verify и проверки» — из ответов модели (не отказ и не fallback) доля
  прошедших verify цитат, проверку чисел и длины. Обрезанный ответ считается прошедшим;
- «LLM: fallback на экстрактив» — доля вызовов, где LLM недоступен, ответил не JSON, не по
  схеме или упёрся в `max_tokens`;
- «LLM: отказ модели» — доля вызовов, где модель вернула `needs_escalation=true`;
- p50/p95 — уже с LLM;
- в `-v` у каждого вопроса `mode=… check=…` и итог «исходы: {ok, truncated, declined,
  verify_failed, foreign_numbers, too_long, fallback}».

Что смотреть: низкий «прошёл verify» с исходом `verify_failed` при pp=1 и заметно выше при
pp=0.3 — значит, presence_penalty портит дословность цитат. «Инъекции отбиты» для LLM
засчитывает ответ, который сослался только на ожидаемый пункт: он уже прошёл проверку чисел.

### Порог gate реранкера на синтетике: 0.1 (история; сейчас 0.2 — «Реальный корпус»)

Подбор на `final` (`--sweep`). Gate-скор вопроса от порога не зависит, поэтому таблица считается
за один прогон:

| Порог | Ответ с верным пунктом | Ложные отказы | Abstain-acc ловушки |
|---|---|---|---|
| 0.02 | 79% | 21% | 75% |
| 0.03 | 76% | 24% | 88% |
| 0.05 | 76% | 24% | 100% |
| 0.07 | 76% | 24% | 100% |
| **0.10** | **72%** | **28%** | **100%** |
| 0.20 | 69% | 31% | 100% |
| 0.30 (старт из ресерча) | 62% | 38% | 100% |
| 0.50 | 59% | 41% | 100% |

Почему 0.1:
- Максимум sigmoid на ловушках — 0.039 («ДМС после испытательного срока»), второй — 0.021
  («доплата за ночную смену»). Начиная с 0.05 все 8 ловушек отказываются.
- 0.05 даёт на один ответ больше (пункт 5.2 со скором 0.083), но запас над худшей ловушкой там
  всего ~0.25 логита. У 0.1 запас ~1 логит (logit 0.1 = −2.2, logit 0.039 = −3.2). Выдуманный
  ответ хуже лишней эскалации, а ловушек всего 8, поэтому запас важнее одного ответа.
- 0.3 из ресерча теряет ещё 3 перефраза со скорами 0.126–0.28 («через сколько можно уехать
  отдыхать», «до скольки я сижу в офисе», «поесть в час дня») и ничего не даёт на ловушках.
- Оговорка: порог подобран на том же golden set, на котором измерен, а корпус синтетический.
  На настоящих документах ПОЛИПЛАСТИК надо прогнать `--sweep` заново, расширив golden set.

Почему реранкер скорит пункты, а не чанки: при скоринге склеенного чанка («2.1+2.2+2.3»,
«3.1+3.2», «5.1+5.2») на этом же наборе «ответ с верным пунктом» был 62% при порогах 0.1–0.3
и 72% только при 0.05, где запас над худшей ловушкой (0.006) ещё меньше. Скоринг по пунктам дал 72–76% при 100% на ловушках, а лучший пункт сразу идёт
в экстрактивную цитату. Пара «раздел. текст пункта» сравнивалась с «документ, раздел, п.: текст»
и с голым текстом пункта. Голый текст поднимал скор ловушки до 0.11, полный заголовок занижал
перефразы.

### Скорость `/ask` (2026-10-24)

Цель — p95 ≤ 3 с без потери качества. До изменений почти всё время уходило на реранкер на CPU
(~1.3 с на 15 пар), первый запрос после старта платил за прогрев, а медленный под LLM держал
`/ask` до 20 с (бот ждёт 8 с).

Что сделано:
- **Устройство моделей `RAG_DEVICE=auto`**: cuda → mps → cpu. На Mac-хосте обе модели идут на
  Apple GPU (mps), FP32. Микробенч на 12 вопросах × 15 пар: реранкер CPU 1319 мс → mps 388 мс,
  эмбеддинг вопроса 143 → 35 мс. Логиты совпадают с CPU до 4-го знака, косинус эмбеддингов 1.00000,
  поэтому порог gate не сдвигается. В Linux-контейнере mps нет, там остаётся cpu.
- **Прогрев на старте** (`Pipeline.warmup`, `RAG_WARMUP=1`): два прогона retrieve+rerank и
  один вызов LLM. Идёт в lifespan до открытия порта, поэтому `/health` отвечает, только когда
  сервис прогрет. Старт с моделями ~16 с. Ошибка LLM в прогреве старт не роняет.
- **LRU-кэши вопроса**: эмбеддинг вопроса и логиты пар (вопрос, пункт), 512 вопросов. Повтор
  вопроса не трогает модели. Кэши от корпуса не зависят и переживают загрузку документа.
- **Бюджет LLM `LLM_TIMEOUT`, по умолчанию 4 с** на весь вызов, а не на фазу httpx. Не
  уложился — дословная цитата лучшего пункта, `mode=extractive_fallback`, `check=fallback:timeout`.
  Так `/ask` укладывается в 8 с бота при любом состоянии пода (на живом прогоне под однажды
  отвечал 13 с). Старое имя `LLM_TIMEOUT_S` тоже читается.
- **`RAG_RERANK_TOP`** — сколько чанков после RRF скорит реранкер (по умолчанию 20). Top-8
  на golden set дал те же метрики и p50 375 мс против 419, но в корпусе всего 10 чанков и
  выигрыш в шуме. Оставлен 20: на настоящем ПВТР надо перемерить `--rerank-top 8`.
- Проверено и не взято: `torch.set_num_threads` 4/6/10 — разница в пределах шума
  (`RAG_TORCH_THREADS` оставлен ручкой); fp16 на mps — 321 мс против 388, но логиты
  сдвигаются на 0.013; ONNX/квантизация — не нужны после mps.

Eval теперь меряет как сервис: перед вопросами `Pipeline.warmup`, перед каждым вопросом кэши
сброшены (холодный вопрос). В `-v` у каждого вопроса задержка.

Golden set, Apple M4, на машине параллельно работали ещё 5 агентов (load average 10–18),
LLM — T-lite на поде, общий с другими агентами:

| Метрика | final до | **final после** | final+llm до | **final+llm после** (`LLM_TIMEOUT=4`) | final+llm, `LLM_TIMEOUT=2.5` |
|---|---|---|---|---|---|
| Hit@5 | 100% | 100% | 100% | 100% | 100% |
| Ответ с верным пунктом | 72% | 72% | 72% | 72% | 72% |
| Abstain-acc на ловушках | 100% | 100% | 100% | 100% | 100% |
| Инъекции отбиты | 100% | 100% | 100% | 100% | 100% |
| Citation-validity | 100% | 100% | 100% | 100% | 100% |
| LLM: fallback на экстрактив | — | — | 0% | 5% (1 verify_failed) | 21% (2 timeout, 2 verify_failed) |
| p50, мс | 1648 | **419** | 1922 | 1821 | 544 |
| p95, мс | 3039 | **481** | 4110 | 4149 | **2857** |

- Без LLM `/ask` ускорился в 4–6 раз и p95 < 0.5 с. На CPU (`RAG_DEVICE=cpu`) после изменений
  p50/p95 1239/1574 мс.
- С LLM хвост — это сам под: прямой замер `/chat/completions` 1.4–2.7 с при ~2800 токенах
  промпта и 24–158 токенах ответа (~19 мс/токен плюс ~1 с на сеть и prefill). Ретривер теперь
  ~0.45 с из этого.
- С бюджетом 4 с p95 упирается в под (3.6–4.1 с). С `LLM_TIMEOUT=2.5` p95 ≤ 3 с при любом
  поде, качество по метрикам то же: на опоздавшие вызовы уходит дословная цитата того же
  пункта. Цена — около 10% ответов LLM становятся цитатой. Для демо с целью ≤ 3 с ставить
  `LLM_TIMEOUT=2.5`.
- `--sweep` после изменений совпал с прежним: max gate на ловушке 0.039, при 0.1 ловушки 100%,
  порог 0.1 не меняется.
- HTTP-смоук на :8095 (40 вопросов golden, LLM включён): `LLM_TIMEOUT=4` — первый запрос
  2.7–3.2 с, p50 0.5–1.5 с, p95 2.9–3.6 с; `LLM_TIMEOUT=2.5` — первый 2.5 с, p50 0.6 с,
  p95 2.6 с, max 2.9 с. Разброс между прогонами — нагрузка на общий под.

### Разговорные перефразы: словарь и переформулировка LLM (2026-10-24)

До этого 58 % разговорных перефразов получали отказ: Hit@5 на них 96 %, нужный пункт находится,
но реранкер ставит паре «пообедать» / пункт об обеденном перерыве 0.001–0.04, как ловушке.
Порогом это не лечится (ловушка 0.102). Сделано два слоя, оба на том же gate 0.2.

**1. Словарь `synonyms.yaml` без LLM** (`query_expand.py`, `RAG_SYNONYMS=rerank`). 19 групп
кадрового сленга: пообедать, перекур, кусками, отгул / за свой счёт, свадьба, задержаться,
проспал, больничный, испыталка, бумаги на оформление, зп / получка, дресс-код, сфоткать,
выговор, откат / взятка, подарок, разболтать. Триггер — леммы подряд, в любой форме. К вопросу
дописываются термины регламента; расширенный вопрос идёт в BM25 и bge-m3, реранкер скорит пункт
исходным и расширенным вопросом и берёт максимум. Только в поиск (`retrieve`) — не помогает:
кандидаты и так находились, проблема в скоре реранкера. Слов ловушек («обед», «премия»,
«опоздать», «проезд») в словаре нет: широкий триггер поднимает их скор.

**2. Переформулировка LLM при провале gate** (`rewrite.py`, промпт `prompts/query-rewrite.md`,
источник истины `agency/prompts/query-rewrite.md`). T-lite за 0.6–1 с даёт 1–3 формулировки
«языком регламента», по каждой — поиск и реранк 4 кандидатов. Первый прогон (берём лучший скор
любой формулировки) поднял перефразы до 73–85 %, но уронил ловушки до 80 %: формулировка
уводит тему («подарок клиента» → «разглашение коммерческой тайны» 0.73) или теряет уточнение
(«опоздать **без последствий**» → пункт о начале рабочего дня 0.58). Поэтому три защиты:

- **согласие**: пункт засчитывается, только если он первый ещё у одного запроса — исходного
  вопроса или другой формулировки. Одна «уехавшая» формулировка ничего не решает;
- **подтверждение LLM**: пункт, найденный только переформулировкой, отдаётся, если модель
  ответила по нему на **исходный** вопрос и ответ прошёл verify. Для legal/security LLM тоже
  вызывается, но ответ — дословная цитата пункта, который она выбрала. Таймаут, ошибка, отказ
  модели или число не из пункта (`foreign_numbers`) — отказ `below_threshold`, а не цитата
  (ловушки «дни на переезд», «такси после задержки» прошли gate через согласие и отбиты здесь);
- код отбрасывает формулировки с числами, которых нет в вопросе, и попавшие в маршрут.

Бюджет: `RAG_REWRITE_TIMEOUT=3` на LLM-формулировку, `RAG_ASK_BUDGET=7.5` на весь `/ask` (LLM
получает остаток), в LLM по переформулировке идут 3 чанка, а не 5 (`RAG_REWRITE_LLM_TOP`): с 5
чанками треть подтверждений упиралась в таймаут. `RAG_REWRITE_SPECULATIVE=1` просит формулировку
параллельно с поиском: −0.6–1 с на p50.

**Отложенный набор `eval/golden-real-holdout.csv`** (в `.gitignore`): словарь писался после
разбора отказов golden-real, поэтому на нём он завышает результат. Отложенный набор составлен до
прогонов: 22 новых разговорных перефраза к тем же пунктам, 10 новых ловушек (спортзал, автобус,
бейдж, мобильная связь, детсад, матпомощь на свадьбу, молоко за вредность, библиотека, переезд,
такси), 2 инъекции.

### Переключение живого rag на реальный корпус

Живой rag запущен через `run.sh` (uvicorn на :8093). Остановить его процесс по PID (не по порту),
затем из `services/rag`:

```bash

until curl -sf localhost:8093/health; do sleep 1; done   # ~20 с: модели + индекс + прогрев
```

`RAG_CORPUS_DIR=testdata/corpus,corpus-real` включает оба корпуса, но для демо не нужен:
синтетика даст ответы, которых нет в регламентах заказчика. Порог и rerank_top совпадают с
новыми значениями по умолчанию, в команде они для явности. Для Docker `corpus-real` в образ не
попадает (`.dockerignore`): монтировать томом и ставить `RAG_CORPUS_DIR=/app/corpus-real`.

Прочие правки по ходу: маршрут `conflict` больше не срабатывает на «конфликт интересов» (это
тема антикоррупционной политики, отвечается по слайду).

## Голос (`asr.py`, `POST /transcribe`)

Распознаёт голосовые новичков из MAX. Бот показывает новичку «🎙 Распознал: …» и дальше ведёт
текст как набранный. Работает локально на CPU: звук и текст за пределы машины не уходят
(п. 4.3.2 Положения). Контракт описан в `agency/system/api_contract.md`, раздел «v4 — Голосовые».

```
multipart audio → ffmpeg (временный файл → PCM s16le, моно, 8 кГц, не дольше 121 с)
  → > 120 с: 413 · RMS < 0.003 (тишина): {"text": ""}
  → T-one (sherpa-onnx OnlineRecognizer, greedy CTC, 4 потока) + 1 с тишины в хвост
  → {"text", "lang": "ru", "duration_s", "confidence": null}
```

Решения:
- **ffmpeg** читает временный файл, а не stdin: у m4a индекс `moov` лежит в конце, и из трубы
  ffmpeg его не находит.
- **Распознаватель** один на процесс и грузится лениво (0,8 с). На старте сервис его прогревает,
  если модель на месте. Разбор идёт под замком: потокобезопасность `decode_stream` не
  документирована, так же сделано в `hack-ru-clinik`.
- Нет модели или ffmpeg — 503, но сервис поднимается: `/ask` работает без распознавания.

### Выбор движка (замеры 24.10, Mac mini M4, только CPU)

Фразы синтезированы `say -v Milena` и пережаты в ogg/opus 24 кбит/с, как голосовые MAX. Время
считалось с ffmpeg, модель уже загружена.

| Фраза (длительность) | T-one (sherpa-onnx) | faster-whisper small int8 | faster-whisper medium int8 |
|---|---|---|---|
| «Когда мне выдадут спецодежду…» (2,8 с) | 0,16 с · **«тогда** мне выдадут спецодежду…» | 1,8 с · «…**спецнеду**…» | 4,2 с · «…**спецдежу**…» |
| «Мастер на смене кричит…» (3,7 с) | 0,17 с · без ошибок | 1,5 с · без ошибок | 4,2 с · «мастер **на СМИ не** кричит» |
| «…где столовая на ГТП…» (4,0 с) | 0,21 с · без ошибок («гтп») | 1,7 с · «столовая **нога Этэпе**» | 3,9 с · без ошибок |
| «Сколько дней отпуска…» (3,6 с) | 0,16 с · «дней **пуска**» | 1,3 с · без ошибок («6») | 4,0 с · без ошибок |
| Жалоба про порез руки (17,4 с) | 0,66 с · «линию экструзия» | 2,2 с · «линию экструзия» | 6,2 с · без ошибок |
| Все пять подряд (31,4 с) | **1,05 с** | 4,4 с (beam 1), 6,4 с (beam 5); потерял «Ещё» | 13,5 с |

Выбрали **T-one** (`sherpa-onnx-streaming-t-one-russian-2025-09-08`, Apache-2.0):
- По качеству на этих фразах T-one и whisper small близки: по 1–2 ошибки на фразу. Whisper
  портит название площадки («нога Этэпе»), T-one слышит его как «гтп».
- По задержке T-one в 4–10 раз быстрее. Голосовое на 30 с распознаётся примерно за 1 с при
  цели < 5 с. Whisper small на 30 с — 4,4 с: впритык на M4 и заметно больше на облачной ВМ.
- Модель весит 138 МБ, torch не нужен, она одинаково работает на macOS и в Linux-образе.
  `mlx-whisper` в Docker не работает.
- Её же использует `hack-ru-clinik`: там это распознавание звонков, ~44× быстрее реального
  времени.

Минусы T-one и что с ними сделано:
- Модель пишет строчными, без пунктуации и цифр. Бот поднимает первую букву для эхо. RAG
  (BM25 + pymorphy) и `parseScore` («восемь») понимают текст без пунктуации.
- Вероятностей нет, поэтому `confidence` всегда `null`.
- Модель обучена на 8 кГц (телефония), и голосовые даунсемплятся до 8 кГц.
- Синтетический голос — не живая речь в цехе. На живых записях с шумом не мерили
  **[проверить]**.

## Что заглушено или не сделано

- `POST /flags` всегда отдаёт `{"flags": [], "sentiment": "neu", "quote": ""}`. В коде оставлен TODO
  под LLM-разметку по таксономии F1–F10 из ресерча (блок C).
- `site` принимается и валидируется, но в поиске пока не участвует: у чанков ещё нет площадки.
- Загруженные документы живут в памяти процесса и пропадают при рестарте.
- `/documents` без авторизации, как и весь сервис: он слушает только loopback, ходит в него
  бэкенд. Права HR на загрузку должен проверять бэкенд.
- Генерация LLM на настоящей модели ещё не прогонялась: тесты на фейковом LLM, метрик
  `final+llm` нет (см. «Оценка с LLM»).
- Эмодзи и Markdown из `answer` код не вычищает (промпт v2, раздел E, правило UX 9).
- Few-shot примеры 1, 2, 4 написаны на «вы», «ты», «вы» при одном `{address_form}` в system:
  так в промпте v2, код передаёт их как есть. Если модель путает форму, это первым делом
  (Tuning notes, п. 5 в промпте).
- Нет LLM-судьи, LLM Guard и fuzzy-сравнения цитат для OCR-шумных сканов. OCR слайдов-картинок
  в PPTX не делается: такие слайды попадают в `low_confidence_pages`.

## Известные ограничения

- BM25 без реранкера синонимов не ловит («потерял пропуск» → отказ). Помогают словарь
  `synonyms.yaml` (расширение вопроса) и маленький `DOC_SYNONYMS` в `textnorm.py` (зарплата →
  заработная плата, расширение документа).
- Перефразы, далёкие от текста, без LLM по-прежнему отказывают: их скор реранкера не отличить от
  ловушек. С LLM их вытаскивает переформулировка вопроса (`rewrite.py`), но только при согласии
  формулировок и подтверждении LLM — часть всё равно уходит человеку («Реальный корпус»).
- Словарь `synonyms.yaml` писался после разбора отказов golden-real: на нём он завышает
  метрики. Честная оценка — отложенный набор `eval/golden-real-holdout.csv`.
- В BM25-режиме слово вопроса, которого нет ни в одном документе, получает максимальный вес.
  На этом держится ловушка «ДМС». Обратная сторона: опечатка в ключевом слове тоже приводит к отказу.
